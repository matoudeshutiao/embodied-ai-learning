# 第 19 天：队列容量与动作时间对齐

> 时间：2026.11.08 ｜ 第 19 天 ｜ ROS2 周 Day 11
>
> 目标：把“队列两条”和“动作过期”这两个规则定清楚，不急着写新功能。

---

## 1. 为什么这两个问题重要

队列不只是“存动作”：

```text
队列长度 → 决定延迟
动作年龄 → 决定执行的是不是旧计划
```

如果只关注“有没有丢动作”，会忽略更危险的情况：

```text
动作没丢，但时间被压缩了
动作没丢，但已经是几秒前的计划
```

---

## 2. 两种队列容量语义

### A. pending-only

```text
active = 正在执行的那一条
pending = 还没开始执行的队列
max_pending = 2
```

系统最多：

```text
1 条 active + 2 条 pending = 总在途 3 条
```

### B. total in-flight

```text
active + pending 最多 2 条
max_in_flight = 2
```

系统最多：

```text
1 条 active + 1 条 pending = 总在途 2 条
```

| 对比项 | A：pending-only | B：total in-flight |
| --- | --- | --- |
| 参数 | `max_pending=2` | `max_in_flight=2` |
| 总在途上限 | 3 | 2 |
| 最坏延迟 | 约 3 条动作 | 约 2 条动作 |
| 丢动作概率 | 较低 | 较高 |
| 计划连续性 | 更好 | 更短 |
| 适合场景 | 静态目标、重视连续性 | 动态目标、重视低延迟 |

---

## 3. 8 条动作的理论时间线

假设：

```text
动作每 0.25 秒到达
每条动作执行 0.6 秒
动作编号 1～8
```

### A：pending-only 2

```text
执行：1, 2, 4, 7, 8
丢弃：3, 5, 6
```

原因：

```text
0.6 秒时第 1 条结束，第 2 条开始执行
所以第 2 条在队列满之前已经变成 active
第 3 条被第 5 条挤掉
```

### B：total in-flight 2

```text
执行：1, 3, 5, 8
丢弃：2, 4, 6, 7
```

原因：

```text
0.5 秒时第 3 条到达
此时 active 是第 1 条，pending 是第 2 条
总在途已经 2 条
所以第 2 条立即被丢弃
```

关键时间点：

```text
1.75 秒第 8 条到达时
第 5 条还在执行到 1.8 秒
第 7 条还在 pending
总在途 2 条
→ 第 7 条被丢弃
```

所以：

```text
B 规则下不会出现“第 7 条执行、第 8 条等待”
```

## 4. 推荐哪种

#### A 的优缺点

优点：

```text
丢动作少
未来计划保留得更多
轨迹连续性更好
```

缺点：

```text
最坏排队延迟多一段动作
header.stamp 更旧
更容易执行几秒前的计划
```

适合：

```text
静态目标
变化很慢的环境
对连续性要求高的任务
```

#### B 的优缺点

优点：

```text
最坏延迟更短
动作更新鲜
时间压缩更少
```

缺点：

```text
压力大时丢动作更多
未来计划更短
连续轨迹更容易被截断
```

适合：

```text
移动目标
动态障碍
真机遥操作
需要快速响应新观测的任务
```

#### 为什么真机推荐 B

不是“丢包越少越好”，而是：

```text
丢一个旧动作
比执行一个过期动作更安全
```

B 丢得更多，但丢的是尚未执行的旧计划；  
A 丢得少，但它可能把旧计划执行到更晚。

#### 当前实现

```text
B 是默认：max_in_flight=2
A 可用：max_in_flight=3
```

参数名已经统一为：

```text
max_in_flight
```

而不是含糊的 `max_queue_size`。

## 5. 动作时间对齐

### 5.1 两个时间不是一回事

```text
header.stamp
= 动作产生/观测的时间

time_from_start
= 轨迹从起点开始要执行多久
```

队列等待会让 `header.stamp` 变旧。

### 5.2 隔离测试发现

8 条动作全部执行，`dropped=0`，但：

| 动作 | 排队延迟 | 实际执行 | 总和 |
| --- | ---: | ---: | ---: |
| #2 | 0.451 s | 0.155 s | 0.606 s |
| #3 | 0.455 s | 0.153 s | 0.608 s |
| #4 | 0.358 s | 0.252 s | 0.610 s |

说明：

```text
控制器把旧时间戳当作轨迹起点
排队越久，剩余执行时间越短
```

这不是丢动作，而是：

```text
动作时间被压缩
实际速度变高
```

### 5.3 为什么控制器会自动压缩

`header.stamp` 是轨迹的绝对起点，`time_from_start` 是每个点相对这个起点的偏移。

```text
header.stamp = 0.0
point.time_from_start = 0.6
```

控制器理解成：

```text
从 0.0 开始，0.6 秒后到达目标
```

如果动作在队列里等了 0.45 秒才被发出，控制器看到：

```text
轨迹起点是 0.0
当前时间已经是 0.45
只剩 0.15 秒
```

于是它只执行剩余的 0.15 秒。

它不是“暂停计时”，而是按时间表执行：

```text
已经到期的部分不等待
剩余部分被压缩
```

所以队列延迟不会自动变成等待，而是会被控制器当成已过去的时间。

## 6. 没写出的那道题

### 题目

```text
一条动作总时长 0.6 秒
它在队列里等了 0.5 秒
现在只剩 0.1 秒
应该执行剩下的 0.1 秒，还是直接丢弃？
```

### 答案不是简单的“二选一”

#### 方案 1：直接执行剩下的 0.1 秒

```text
不推荐
```

原因：

```text
路径被压缩到 1/6 时间
实际速度可能变成原计划的 6 倍
跟踪误差、保护性停机、碰撞风险
```

而且这 0.6 秒动作是基于旧状态算的，场景可能已经变化。

#### 方案 2：直接丢弃

```text
默认更安全
```

适合：

```text
VLA 基于最新图像生成的动作
移动目标
动态环境
无法确认当前状态与轨迹起点一致
```

丢弃后应该：

```text
请求新动作
或保持当前位置
或进入安全停止
```

#### 方案 3：重新对齐后执行

```text
条件满足时才允许
```

条件：

```text
目标是静态的
路径仍然有效
当前关节位置与轨迹起点足够接近
无障碍物变化
重新计时后速度不超限
```

做法：

```text
用当前状态重新计算轨迹
重新设置 header.stamp
重新分配安全的 time_from_start
```

不能直接把剩下的 0.1 秒原样发给控制器。

### 最终规则

```text
默认丢弃过期动作
只有在确认安全、路径有效、可以重新计时时，才执行重新对齐后的动作
永远不要原样执行“只剩 0.1 秒”的旧轨迹
```

## 7. 代码实现

已完成：

```text
1. 统一容量参数为 max_in_flight
2. 默认 max_in_flight=2（B）
3. 可用 max_in_flight=3 近似 A
4. 出队时计算 age = now - header.stamp
5. age 超过 max_action_age → 丢弃
6. 可执行时重新设置 header.stamp = now
```

新增参数：

```text
max_action_age = 0.5 秒
```

launch 参数：

```text
max_action_age:=0.5
max_in_flight:=2
```

测试目标：

```text
正常动作是否按完整时长执行
过期动作是否被丢弃
队列丢最旧策略是否符合容量语义
```

## 8. 今天要记住的三句话

```text
队列容量要明确是否包含 active
动作年龄比动作数量更危险
过期动作默认丢弃，重新对齐是例外，不是默认
```
